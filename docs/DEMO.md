# 面试演示脚本（无人机选址 Agent）

> 目标：在 6~8 分钟内，用可复现的操作展示「Agent 自主调用工具 → 基于真实数据作答 → 多轮记忆 → 协议层复用」四件事。
> 所有数字均为本仓库样例实测值，换数据会变，讲解时以现场屏幕为准。

## 0. 启动（30 秒）

```powershell
cd community_supermarket_site_selection
python app.py
```

- 看板：http://127.0.0.1:5001/
- Agent：http://127.0.0.1:5001/agent
- 前提：`.env` 里配置 `DEEPSEEK_TOKEN`（或 `DEEPSEEK_BASE` 指向的兼容端点）、`AMAP_KEY`
- 境外模型端点需要代理：`agent_llm.py` 已按系统代理发起请求，无需额外设置环境变量

## 1. 主线演示：深圳选址（约 1~2 分钟）

**输入（城市选 shenzhen）**

```
请对深圳做一次完整选址，P 取 1,3,6,10 做对比，给出推荐方案，并把推荐机坪的位置转成商圈名
```

**预期工具轨迹（可在页面轨迹区逐条展开）**
1. `run_site_selection(city="shenzhen", p_values="1,3,6,10")`
2. `regeo_label(lat, lon)` × 推荐机坪数量

**实测结果（本仓库样例数据，可直接对照）**

| P | 覆盖起降点 | 覆盖单量权重 | 平均距离 km |
|---|---|---|---|
| 1 | 2 | 4104.0 | 0.000 |
| 3 | 8 | 4104.0 | 0.000 |
| 6 | 14 | 10881.0 | 0.000 |
| 10 | 21 | 13401.0 | 0.273 |

推荐方案 **P=10**，10 个机坪，10 个商圈标签（如 `南山区 粤海街道 商圈:后海`、`南山区 招商街道 商圈:蛇口`）。

**讲解要点（按顺序说，每点一句）**
1. 漏斗：347 个候选起降点 → Stage1 通过 116 → Stage2 选中 2 → Stage3 覆盖 21（P=10）。
2. 推荐不是看单量最大，而是「覆盖点数降序、平均距离升序」——因为当前阶段是纯物理网络，不算财务 ROI。
3. 商圈名来自高德逆地理编码，Agent 自己决定去调 `regeo_label`，不是代码里写死。
4. P=1、P=3 覆盖单量相同、平均距离 0.000：因为样例里 5 个存量起降点单量为 0 且与机坪同址，多覆盖的是它们。这是数据特性，讲清楚比藏起来更可信。

## 2. 追问：验证多轮记忆（约 30 秒）

同一会话直接发：

```
那 P 只给 6 会怎样？和刚才的推荐方案比差多少？
```

预期：Agent 记住上一轮结果，重新只跑 P=6 并做对比，不会重新问「哪个城市」。
页面刷新后历史仍在（会话落盘在 `agent_outputs/sessions/`）。

## 3. 知识库问答：验证 RAG 与引用（约 30 秒）

```
单个机坪最多服务几个起降点？净空高度最低要求是多少？只查知识库，不要跑选址
```

预期：调用 `rag_retrieve`，回答 **11 个**、**3 米**，并给出出处（如 `stage_pipeline.md#段25`、`domain_rules.md#段5`）。
边界外问题（如「推荐一部电影」）应被覆盖度门槛拦掉，不硬答。

## 4. 自定义数据（可选，约 1 分钟）

上传 `sample_data/shenzhen/` 下的三份 CSV 并提问「用我刚上传的数据跑深圳选址」，观察 `load_csv` 返回 `dataset_id`，后续 `run_site_selection` 带上该 id。

三个必讲的坑：
- 缺 `city` 列会被城市过滤成空结果（系统会自动补全并给警告）
- 机坪缺 `altitude_limit_m` 会按 0 处理，被「净空 < 3 米」全部剔除
- 服务重启后 `dataset_id` 失效（数据集只存在进程内存里），需重新上传

## 5. MCP：协议层复用（约 1 分钟，命令行演示）

```powershell
echo '{"jsonrpc":"2.0","id":1,"method":"tools/list"}' | python mcp_server.py
```

返回 5 个工具：`run_site_selection / load_csv / get_city_configs / regeo_label / rag_retrieve`。

长任务保活：客户端带 `progressToken` 时，选址执行期间每 5 秒收到一条 `notifications/progress`。
实测 38.5 秒的 `run_site_selection` 共发出 9 条进度通知（0~8），最后返回结果。

## 6. 架构四层（白板讲，30 秒）

1. **工具层** `agent_tools.py`：选址、装载数据、检索、逆地理，统一 OpenAI function schema
2. **编排层** `agent_orchestrator.py`：多轮循环、只读并行、checkpoint 续跑、trace 记录、上下文裁剪
3. **上下文层**：分层 system 提示（领域常识 + 工具规范 + 工作流）+ RAG 召回 + 会话历史
4. **协议层** `mcp_server.py`：同一批工具以 MCP 标准暴露，业务实现零重复

## 7. 必须主动交代的边界（面试加分项）

- 覆盖单量是样例合成权重 `rf_sales_10k`，**不是真实日单量**
- 平均距离含同址 0 距离边，会把均值拉低
- 数据集注册表在进程内存，重启失效
- MCP 进度心跳只能缓解超时，硬超时很短的客户端仍会断开；彻底解决需要两段式任务接口
- 模型通道依赖境外端点时需代理，国内端点可直连

## 8. 可能被追问的问题

| 问题 | 回答落点 |
|---|---|
| 为什么不用 LangChain？ | 编排只有 200 行，自己实现便于讲清每一步；引入框架会掩盖 trace 与并行控制 |
| RAG 为什么不上向量库？ | 当前 129 片段，TF-IDF 实测 100% 覆盖、0% 负例误召回；规模到千级再换 |
| 怎么证明不是编的？ | `eval_rag.py` 可复跑；回答带 `文件名#段N` 出处；工具返回与结论数字一一对应 |
| Agent 的核心难点？ | 上下文工程（裁剪/压缩）+ 工具结果瘦身（返回摘要而非完整 result）+ 防死循环 |
